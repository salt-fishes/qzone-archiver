# QZoneArchiver 桌面版 架构改造计划（v4.0.0 → v4.2.0）

> 依据：《架构分析报告.md》与《锐评》结论。原则：**先止血、再契约、后重构；每一步可独立交付、可回滚、行为等价优先于美化。**
> **状态（2026-08-31）：已实施收官** —— P0~P5 全部完成，P6 贯穿项（结构化日志/冒烟清单）已落地，vitest 140 项、CI 四门禁常绿。各阶段执行结论见 §2.1（P0）/§4.5（P2）/§5.5（P3）/§6.4（P4）/§7.4（P5）/§8.3（P6）；全景分析见 [架构全景分析.md](架构全景分析.md)。

## 0. 目标与成功标准

**改造目标**：在不改变产品能力（内嵌登录→采集→打包→SPA 浏览）与备份产物格式的前提下，用 6~8 人周把系统从"全局符号装配 + 字符串契约 + 三份并行状态机"演进为"契约单一来源 + 状态单一事实源 + 引擎真正五层 + 有类型与测试门禁"。

**成功标准（可验收）**：
1. 删除任一死通道/死文件后，全链路（登录→备份→取消→再备份→浏览产物）行为不变；
2. 引擎窗口主世界不再暴露任何 `engineBridge` 能力；`ipc/engine.js` 全部 handler 有来源校验；
3. `npm run typecheck && npm run lint && npm test` 全绿并进入 CI 门禁；
4. UI 与引擎配置、模块清单各只剩一份定义（生成，非手抄）；
5. 备份失败模块在成功页显著可见，无静默"成功"；
6. 取消备份后再次备份，媒体下载可正常调度（当前缺陷修复）。

## 2. P0 止血（4.0.1，1~2 人日）

### 2.1 修复取消后备灾下载调度（P0-1）

**缺陷**：`downloadManager.cancel()` 置 `paused=true`；`backup:start` 只调 `engineBridge.start()`，从不恢复下载调度；`pump()` 首行 `if (paused) return` → **取消过一次后，后续备份的媒体下载全部静默排队**，直到重启应用。

**改造（文件：`src/main/services/download-manager.js`、`src/main/ipc/backup.js`）**：
1. 语义拆分：`cancel()` 只做"中断运行中任务 + 清空 pending"（不清 paused）；`pause()`/`resume()` 独占暂停语义（与 `backup:pause/resume` 的联动已存在，保持）。
2. `backup:start` handler 显式调用 `downloadManager.resume()`（幂等），确保每次新备份调度器处于可泵状态。
3. 加一个最小状态断言：`enqueue` 时若 `paused` 且无进行中备份任务，记 warning 日志（后续 P3 由任务状态机根治）。

**验收**：备份→取消→立即再备份，下载列表出现 running 条目且文件落盘；重复 3 次循环无泄漏。

### 2.2 移除主世界引擎桥（P0-2，头号安全项）

**缺陷**：`src/preload/engine-bridge.cjs` 第 18 行 `exposeInMainWorld('engineBridge', bridge)` 把 invoke/post 原语暴露给 qzone 页面主世界；`ipc/engine.js` 无来源校验 → qzone 页面任何 XSS/第三方脚本可 `engine:fs-remove('/')` 递归删除用户备份目录。

**已验证事实**：引擎脚本全部经 `executeJavaScriptInIsolatedWorld(100)` 注入，`engineBridge` 唯一消费者是隔离世界内的 desktop-adapters.js → **主世界暴露纯属死代码**。

**改造**：
1. `engine-bridge.cjs`：删除 `exposeInMainWorld`，仅保留 `exposeInIsolatedWorld(ENGINE_WORLD_ID, ...)`。
2. `ipc/engine.js`：新增统一守卫函数 `assertEngineSender(event)`，对**全部** engine:* handler 生效：
   - `event.sender` 必须是 `windows.engine.webContents`；
   - `event.senderFrame` 必须存在且为主框架（`frame === frame.parent` 为空或 frame 层级校验）；
   - `event.senderFrame.url` 必须为 `https://user.qzone.qq.com` 前缀（与 index.js 的 did-navigate 判定一致）。
3. 守卫失败返回 `{ ok:false, error:'FORBIDDEN' }` 并告警日志。

**验收**：主窗口 DevTools 中 `window.engineBridge === undefined`（引擎窗主世界同样）；正常备份全链路无回归；在引擎窗主世界手动调用（如有残留入口）被拒。

### 2.3 备份失败可见性（P0-3）

**缺陷**：模块层 `catch { console.error }` 吞错；orchestrator 记 `results[mod]='error'` 后整体仍推 `completed`；成功页全绿。

**改造**：
1. `tasks/orchestrator.js`：runModule 捕获异常时构造结构化错误 `{ module, phase, message, stack }` 存入 `s.errors[]`，`completed` 通知 payload 增加 `errors` 字段（经 `engine:notify` state 透传，主进程 `backup:completed` 原样转发）。
2. `stores/backup.ts`：`lastResult` 增加 errors；`components/backup/SuccessPanel.vue`：存在 errors 时置顶红色"部分模块备份失败"区，列出模块中文名 + 错误信息 + 重试提示。
3. `exportLogs` 已含日志，无需改动；确保模块 error 行（orchestrator 已有 log error）被保留。

**验收**：人为构造单模块失败（如断网）→ 成功页显示失败模块与原因，而非全绿；`report.json/manifest.json` 不因失败标记为成功。

## 3. P1 契约固化（4.1，3~5 人日）

### 3.1 共享契约模块
- 新建 `src/shared/ipc-contract.mjs`：集中全部通道名常量（`UI_INVOKE`、`UI_PUSH`、`ENGINE_INVOKE`、`ENGINE_POST` 四组 + JSDoc 载荷类型）。main/ipc/*、main/services/*（sendToUi 调用点）全部改为引用常量。
- preload 迁移 `.cjs → .mjs`（当前 `sandbox:false` 已满足 ESM preload 前提），`ui-bridge` 的 `PUSH_CHANNELS` 白名单与 `api` 分组、`engine-bridge` 通道均引用同一契约模块 → 白名单与 handler 永不漂移。
- 渲染层 `env.d.ts`：新增 `scripts/gen-contract-types.mjs` 扫描 preload 导出生成 `window.api` 类型（或人工一次性对齐 + CI diff 检查），纳入 `npm run typecheck`。
- 实施约束：共享契约为 `.mjs`，而 CJS 无法同步 require ESM——契约文件引入与两个 preload（`ui-bridge.cjs`/`engine-bridge.cjs`）的 `.mjs` 迁移必须在**同一提交**完成，避免出现 require 不了 .mjs 的中间态。

### 3.2 死代码清理
- 删除：`log:batch`（白名单+无发送方）、`engine:ready`（空 handler）、`download:start`（UI 未调用且语义已被 backup 链路覆盖——先 grep 确认无引用）、`env.d.ts` 中渲染层未用的声明。
- 归档：`src/engine/content.js`、`background.js` 移入 `docs/legacy-extension/`（保留 git 历史），并在 README 注明"扩展端遗留，桌面版不注入"。
- `api.on` 白名单同步收缩到实际使用集合（`zip:progress` 若 P1 不接 zip UI 则一并移除；若保留则写 TODO 注明归属阶段）。
- 决策点（P1 评审确认）：渲染层当前完全无 zip UI（`window.api.zip` 零调用），`zip:create` handler、`zip:progress` 通道与 packager 构成半清理态——要么整链保留（统一写 TODO），要么 handler + 通道 + packager 一并归档，禁止只删通道留实现。

### 3.3 模块清单单一来源
- 新建 `src/shared/modules.json`：`[{ key, zh, exportable }]`（Statistics 标记 `exportable:false`）。
- 消费方：渲染层 `stores/config.ts` 的 MODULES/MODULE_META 改为 import；引擎 `config.js` 的 `MODULE_NAME_LIST` 与 orchestrator `MODULE_NAMES` 改为注入时从 `resources.readText('modules.json')` 构建；`scripts/sync-baseline.mjs` 同步该文件。

### 3.4 质量门禁
- `package.json` scripts：`typecheck`（`vue-tsc --noEmit` + 对 main/ 的 js 开 `tsc --allowJs --checkJs --noEmit`）、`lint`（ESLint flat config + eslint-plugin-vue）、`test`（vitest 起步，先覆盖 §6.2 纯函数）。
- CI（GitHub Actions）：PR = typecheck + lint + test；main = 同上 + `npm run build:renderer`。

**验收**：任何新通道必须改契约文件（review 可见）；`typecheck/lint` 首跑后清零存量错误（允许一次性 `// TODO` 豁免清单，逐阶段消除）。

## 5. P3 状态与增量重构（4.2，5~10 人日）

### 5.1 任务状态机（单一事实源）
- 新建 `src/main/services/task-machine.js`：状态转移表 `idle → preparing → running → paused ⇄ running → cancelled | completed | failed`；持久化到 checkpoint 文件；**主进程是状态唯一裁判**，引擎 notify 只是输入事件，渲染层状态全部由 `backup:state-changed` 派生（删除渲染层乐观置位与引擎/主进程/渲染层三份并行状态）。
- `engineBridge.pause/resume/cancel` 命令由状态机 guard（非法转移拒绝并告警）。
- `backup:get-state` 返回状态机快照；checkpoint 只存最小恢复上下文（taskId/targetDir/modules/config）。
- 备份失败明细持久化（P0-3 遗留项）：P0-3 仅将 errors 透传到成功页，`backup-history.json`/`recordBackup` 链路仍不记录模块级失败——重启应用后历史记录显示假成功。P3 随状态机一并落库。

### 5.2 下载管理器并入任务机
- 删除模块级 `paused` 全局（P0-1 的根因），改为任务级状态；`downloadManager` 只认"当前活跃 taskId"的暂停位 → cancel/pause 跨任务泄漏从机制上消灭。

### 5.3 增量元数据落产物
- `Backedup` 从 `engine-storage.json`（主进程 userData）迁移到**产物目录** `Common/backup-meta.json`（含每模块 lastTime/lastDataHash）；`initBackedUpItems` 改从 `QZonePlatform.fs` 读产物目录；`engine-storage` 仅保留配置与"上次备份目录指针"。
- 收益：换目标目录/产物被删后增量语义自然失效（不再"磁盘没了 storage 还在"）；备份目录可整体迁移而不丢增量能力。
- `manifest.generate` 同时更新 backup-meta（manifest.json 是"这次"，backup-meta 是"截至这次"）。
- 写放大治理：`saveBackupItems` 按模块分文件写（`Common/meta/{Module}.json`），不再全量 `storage.set`。

### 5.4 主进程统计异步化
- `backupStats.recordBackup` 中的 `dirBytes/countFiles` 移入 `worker_threads`（或分片 `setImmediate` 让步），杜绝备份完成瞬间主进程事件循环卡顿。

**验收**：删除产物目录后重启备份 = 全量；保留产物换 UI 目标目录重备 = 增量照常；备份完成后主进程无 >100ms 同步阻塞（简单计时探针）。

### 5.5 P3 执行结论（2026-08-28 收尾）
- P3-1~P3-4 全部完成。四门禁（typecheck / lint 0 error / build:renderer 82 modules / vitest 124 项 = 96 旧 + 28 新增）全绿。
- **P3-1 任务状态机**：新建 `task-machine.js`（转移表 + guard：非法转移拒绝告警、同态幂等、prepare 可自终态发起）；主进程唯一裁判，引擎 notify 降为输入事件；模块级失败明细随 complete 落库（P0-3 遗留项闭环）。9 项单测。
- **P3-2 下载管理器并入任务机**：删除模块级 `paused` 全局（P0-1 根因），改任务级暂停位——绑定发起 pause 时的活跃 taskId，pump 时任务已切换则旧暂停位自动失效；无活跃备份用 `STANDALONE_PAUSE` 哨兵。取消/换任务后无需手动 resume。4 项单测含 P0 回归项（任务切换旧暂停位失效）。
- **P3-3 增量元数据落产物**：`saveBackupItems` 双写产物 `Common/backup-meta.json`（结构 `{ Backedup: { [uin]: rows } }` 与 storage 同构）；`getBackupItems` 双读（产物本 uin 键命中优先；产物缺失/损坏/仅他 uin 时回退 engine-storage）；`manifest.generate` 收尾同步重写 backup-meta（manifest 是"这次"，backup-meta 是"截至这次"）。产物写失败仅告警不阻断。7 项单测。
- **P3-4 统计异步化**：`dirBytes/countFiles` 改 `fs.promises` 逐目录 await（让出主线程，预算/截断语义不变）；`recordBackup` async 化，completed 推送不再被目录统计阻塞（fire-and-forget + 完成后推 `backupHistoryChanged`）；`scanBackups` 的 `findBackupDirs` 一并异步化。8 项单测（真实临时目录）。
- **偏差记录**（相对 §5.3 原文，均为有意取舍）：
  1. backup-meta 采用**单文件**而非按模块分文件（`Common/meta/{Module}.json`）——与 engine-storage/`助手备份数据_{uin}.json` 结构同构，读写零转换；分文件的写放大收益在当前数据量级不显著，留待实测后评估。
  2. `storage.set(Backedup)` **过渡期保留**（双写）——§6 迁移期兼容要求双读过渡一个版本；若写侧立即移除，升级后首次备份在产物写失败/中断时会丢增量基线。下一版本清理后即达 §5.3 目标形态（engine-storage 仅剩配置与目录指针）。
  3. 未引入 lastDataHash——现有增量判断依赖 `IncrementTime` 字段比对，hash 无消费方；逐字搬迁铁律下增量行为零变化。
- **遗留**：§5 验收三条（删产物重备=全量 / 换目录重备=增量照常 / 完成瞬间主进程无 >100ms 阻塞）待人工冒烟确认。

## 6. P4 渲染层工程化（4.2，5~10 人日）
