# 更新能力评估（P5.3 §7.3）

> 状态：评估（**不承诺本期落地**） · 日期：2026-08-31 · 结论先行：**建议做，但等发布节奏稳定后**；技术方案采用 electron-updater + 自建静态源（generic provider），工作量 2~3 人日。

## 1. 现状

- 当前更新方式：用户手动从发布页下载新安装包覆盖安装（NSIS 安装版 + portable 免安装版）。
- 无版本检查、无更新提示；用户留存依赖自主回访。
- electron-builder 已具备打包基础（`dist:win`），开启自动更新的边际成本低。

## 2. 方案对比

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **electron-updater + generic 静态源** | 官方方案、成熟稳定；只需一个可静态托管 `latest.yml` + 安装包的 HTTP 源；支持差量更新（blockmap） | 需要自建/租用静态源；portable 版无法自更新 | **推荐** |
| electron-updater + GitHub Releases | 零自建成本 | 国内访问 GitHub 不稳定，目标用户（QQ空间备份用户）在国内，下载成功率差 | 备选，不作主方案 |
| 自研更新检查（版本 JSON + 打开下载页） | 最轻（0.5 人日） | 用户仍需手动下载安装，体验提升有限 | 作为过渡方案可行 |
| 内置完整更新 UI（自研全量） | 完全可控 | 重复造轮子，维护成本高 | 否决 |

## 3. 推荐方案要点（electron-updater + generic 静态源）

1. **静态源**：任意静态文件服务（Nginx / 对象存储 + CDN），目录结构：
   ```
   https://updates.example.com/qzone-archiver/
   ├── latest.yml          # electron-builder publish 自动生成
   ├── qzone-archiver-4.2.0-setup.exe
   └── qzone-archiver-4.2.0-setup.exe.blockmap
   ```
2. **打包配置**（electron-builder `publish` 字段指向 generic 源）；发版流程 = 改版本号 → `npm run dist:win` → 上传产物到静态源，可 CI 化（GitHub Actions 构建后推送）。
3. **应用侧**：`autoUpdater.checkForUpdates()` 轮询（建议启动后 + 每 24h）；下载完成后**用户确认再重启安装**，不做静默重启（备份场景不可打断运行中任务——更新前须检查 `taskMachine` 无 running/paused 任务）。
4. **portable 版**：无法自更新，应用内提示「请到发布页下载新版」即可（检测到 portable 环境时降级为跳转提示）。
5. **签名**：无代码签名证书时 Windows SmartScreen 会拦截安装包；electron-updater 本身可用，但**建议将购买签名证书纳入发版前置项**，否则自动更新下载的包在用户侧可能被拦截（与手动下载同等风险，不恶化）。

## 4. 风险与前置条件

- **静态源可用性**：源挂了 = 全量用户无法更新；需监控或至少多源 fallback（electron-updater 支持多 provider 顺序尝试）。
- **备份不可中断**：更新确认框必须在任务终态才可点击「重启并安装」，否则禁用——实现时的硬性约束。
- **版本兼容**：4.x 的 backup-history / backup-meta 结构已在 P3 固化，更新无需迁移；若未来产物结构变更，沿用双读过渡约定（P3 模式）。

## 5. 结论

- 方案可行、成本可控（2~3 人日 + 1 个静态源），建议在**发布节奏进入常态化（有真实用户回访）后**排期；
- 本期仅产出本评估文档，不在 P5 落地（与计划 §7.3「不承诺本期落地」一致）。
